# 决策记录（decision log）

> 这里放**带日期的决策与事故记录**：为什么当初这么定、那次事故的取证链、代价与后续。
> 架构与约定本身写进 `docs/engineering/`；一次性审计报告写进 `docs/audits/`。

## 为什么单独一份，而不是塞进 CHANGELOG

`CHANGELOG.md` 是 `tools/gen-changelog.mjs` 从 git log 生成的，**下一次发布会整体覆盖**——手写的"为什么"在里面活不过一个版本。而"为什么"恰恰是最贵的部分：三个月后没人记得为什么表前缀不跟着改名、为什么门禁只跑第一道。

所以规则是：

- **变更事实**（改了什么文件）→ 提交信息 + CHANGELOG；
- **决策理由**（为什么这么改、否掉了什么、代价是什么）→ 本目录；
- **一次性结论**（审计/对标/排查）→ `docs/audits/` 或本目录（若含决策）。

## 命名与结构

文件名 `YYYY-MM-DD-<slug>.md`，slug 用英文短横线（如 `2026-10-07-rename-scope.md`）。正文建议按这五段写，缺一段就说明这件事还没想清楚：

```markdown
# <一句话标题>

- 日期：YYYY-MM-DD
- 状态：已定 / 观察中 / 已废弃
- 影响面：<后端 / 前端 / 数据库 / 部署 / 门禁>

## 背景
出了什么问题，证据是什么（数字、路径、复现步骤）。

## 决策
定了什么。一句话能说清就先说清，再说边界。

## 代价与否掉的方案
为什么不选另一个；现在背着什么债。

## 后续
什么时候该重新审视；谁负责。
```

## 两条硬规矩

1. **只追加，不改写**。排查类记录要保留完整的取证链：哪一轮假设被证伪、为什么——改掉它就等于把"我们怎么学会的"删了。要修正结论就新开一篇并在旧文顶部加一行"已被 YYYY-MM-DD 那篇取代"。
2. **不写会泄漏的东西**：真实口令、内网地址、活的主机端口、与泄漏叙述并列的提交哈希。`tools/repocheck/doc_redaction_test.go` 会拦其中一部分；它拦不全，剩下的靠这条规矩。
